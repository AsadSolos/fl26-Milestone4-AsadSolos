M5 – Thread-Safe Design
AI Workspace semester project · Milestone 5 specification · posted November 8, 2026
Phase 2, final milestone: independent engineering. As in M4, this specification defines the
problem, required behavior, and constraints, not the design. You decide your classes, states, and
threads, justify them, and verify them with your own tests. Missing detail is intentional.
Questions that clarify a requirement are welcome; questions about how to design it will be
answered with questions that help you reason it through. This is the last milestone, and it is short
on purpose (12 days, two topics, no change request): the design decisions and the video are
there so that what you learn is visibly yours. Finish by November 20 for the bonus, and enjoy the
break.
1. Overview
Release: November 8 | Due: November 20, 11:59 pm (full credit through November 23, 11:59 pm) |
Value: 20 points, plus a 1-point on-time bonus | Prerequisite: your completed M4, including CR-1
In M5 your application keeps doing what M4 does, but its background work becomes synchronized
and its corpus logic becomes the State pattern. M5 applies Thread Synchronization (Nov 3) and the
State pattern (More on Design Patterns, Nov 12). Thread-safe queues with many items, thread pools,
and task systems are covered in lectures but not required. Expect about 12 to 15 hours of work in
total.
Your starting point is your own M4. The final project integrates every milestone, so M5 is built on
the M4 you submitted, and no M4 solution is released. If anything in your M4 does not work, fix it
yourself before you build M5 on it: the M3, M4, and CR-1 tests are rerun on your M5 submission.
Record what you fixed in DESIGN.md (Section 9).
2. How M5 is assessed
AI tools are permitted. M5 has no design checkpoint, quiz, or TA interview. Instead, you record a short
walkthrough video of your own code (Section 9). All 20 points are graded from your submission, by
the autograder and by hand (Section 10). Separately, the final exam includes questions about
your own M5 design: your states and how they change, how your worker waits and stops, and
what your code does when an event arrives at an awkward moment. They count toward the final
exam grade, so submit only code you can explain.
3. The problem
M4 kept the corpus build off the GUI thread while the M3 invariant held:
Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.
M4 excluded synchronization, so most M4 designs start new background work for every build, cannot
stop a build once it has started, and track the corpus with flags or an enum checked across
MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?
5. What is fixed and what is your design
Fixed (what the graders depend on):
Everything fixed in M4 stays fixed: the M1/M2 headers and the ProcessingCore API, the M3 GUI
public API and button labels, add_document_file() , set_build_delay_ms() , the rule for
src/main.cpp , and aiws_send with its command line.
Rename your application target from ai_workspace_m4 to ai_workspace_m5 before your
first submission; without it, the autograder cannot run your application. CMake builds
ai_workspace_m5 , aiws_send , and a CTest test named student_tests .
Everything else is your design: your classes, your states, what each state does on each event,
how a request reaches the worker, and how a running build learns that it should stop.
6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.
M5_Specification.pdf 2 / 4
3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,
busy waiting, or sleeping to wait for an event; sleeping is allowed only to simulate build time.
4. Shared data is minimal and named. Every piece of mutable data reachable from two threads
is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.
5. M4 constraints still apply: C++ standard library threading only (no QThread , QtConcurrent ,
QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
the CR-1 socket rules.
7. Testing and fault-detection evidence
A test is worth something only if it fails when the code is wrong. Add each defect below to your code
under its macro, at the place in your design where that behavior is decided, in a few lines.
Macro When defined, your application… Breaks
AIWS_FAULT_NO_CANCEL lets a build that is no longer wanted run to the end, so the
next build waits for it
R3
AIWS_FAULT_SILENT_SHUTDOWN makes Exit hang when no build is running R4
The autograder builds your project normally and once per macro. student_tests must pass on the
normal build and fail within 60 seconds on each faulted build. Neither your test files nor
CMakeLists.txt may mention the macros, and each fault must produce the user-visible defect
described.
Beyond the faults, test R1 to R5 at whatever level your design allows. Tests must be deterministic
and bounded in time.

9. Deliverables
M5_Specification.pdf 3 / 4
Submit the whole project, but not build/ , plus:
DESIGN.md , at most one page (about 500 words), replacing your M4 DESIGN.md and naming your
own classes and functions:
1. M4 fixes: anything in your M4 that did not work and how you fixed it, or "none".
2. Threads and shared data: each thread, and the statement required by constraint 4.
3. States: each state, what it means, and which events change it, as a table or a diagram.
4. One event sequence that threatens R1 to R4, traced step by step through your functions on
both threads.
5. Your answers to the three decisions in Section 4, one or two sentences each, naming the
functions that carry them out.
6. Where each fault switch is and which test catches it.
7. AI-use disclosure, required but ungraded.
HISTORY.txt , the output of git log --stat --date=iso , showing work across both weeks.
Walkthrough video, one video of at most 3 minutes. Put its link in a file VIDEO.md at the top of
your submission, shared so that course staff can view it. Record your screen and your own voice
(camera optional) while you show your code and your running application, and explain in your
own words:
1. how your worker gets its next build, and how it stops at exit;
2. Reset during a long build: run your application with --build-delay-ms 500 and press Reset
during a build; then rebuild with -DAIWS_FAULT_NO_CANCEL , repeat it, show the difference, and
explain in your code why it changes (you may cut the rebuild out of the recording);
3. one state transition in your code, from the event to the new state.
The video is graded on whether you can explain your own design, not on polish.

3. The problem

Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.

MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?
5. What is fixed and what is your design
Fixed (what the graders depend on):
Everything fixed in M4 stays fixed: the M1/M2 headers and the ProcessingCore API, the M3 GUI
public API and button labels, add_document_file() , set_build_delay_ms() , the rule for
src/main.cpp , and aiws_send with its command line.
Rename your application target from ai_workspace_m4 to ai_workspace_m5 before your
first submission; without it, the autograder cannot run your application. CMake builds
ai_workspace_m5 , aiws_send , and a CTest test named student_tests .
Everything else is your design: your classes, your states, what each state does on each event,
how a request reaches the worker, and how a running build learns that it should stop.
6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.
M5_Specification.pdf 2 / 4
3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,
busy waiting, or sleeping to wait for an event; sleeping is allowed only to simulate build time.
4. Shared data is minimal and named. Every piece of mutable data reachable from two threads
is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.
5. M4 constraints still apply: C++ standard library threading only (no QThread , QtConcurrent ,
QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
the CR-1 socket rules.

3. The problem

Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.
M4 excluded synchronization, so most M4 designs start new background work for every build, cannot

MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?
5. What is fixed and what is your design

public API and button labels, add_document_file() , set_build_delay_ms() , the rule for

Everything else is your design: your classes, your states, what each state does on each event,

6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.
M5_Specification.pdf 2 / 4
3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,
busy waiting, or sleeping to wait for an event; sleeping is allowed only to simulate build time.
4. Shared data is minimal and named. Every piece of mutable data reachable from two threads
is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.
5. M4 constraints still apply: C++ standard library threading only (no QThread , QtConcurrent ,
QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
the CR-1 socket rules.

In M5 your application keeps doing what M4 does, but its background work becomes synchronized
and its corpus logic becomes the State pattern. M5 applies Thread Synchronization (Nov 3) and the
State pattern (More on Design Patterns, Nov 12). Thread-safe queues with many items, thread pools,

2. How M5 is assessed
AI tools are permitted. M5 has no design checkpoint, quiz, or TA interview. Instead, you record a short
walkthrough video of your own code (Section 9). All 20 points are graded from your submission, by
the autograder and by hand (Section 10). Separately, the final exam includes questions about
your own M5 design: your states and how they change, how your worker waits and stops, and
what your code does when an event arrives at an awkward moment. They count toward the final
exam grade, so submit only code you can explain.
3. The problem
M4 kept the corpus build off the GUI thread while the M3 invariant held:
Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.
M4 excluded synchronization, so most M4 designs start new background work for every build, cannot
stop a build once it has started, and track the corpus with flags or an enum checked across
MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?

M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add

R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.

threads, justify them, and verify them with your own tests. Missing detail is intentional.
Questions that clarify a requirement are welcome; questions about how to design it will be
answered with questions that help you reason it through. This is the last milestone, and it is short
on purpose (12 days, two topics, no change request): the design decisions and the video are
there so that what you learn is visibly yours. Finish by November 20 for the bonus, and enjoy the
break.
1. Overview
Release: November 8 | Due: November 20, 11:59 pm (full credit through November 23, 11:59 pm) |
Value: 20 points, plus a 1-point on-time bonus | Prerequisite: your completed M4, including CR-1
In M5 your application keeps doing what M4 does, but its background work becomes synchronized
and its corpus logic becomes the State pattern. M5 applies Thread Synchronization (Nov 3) and the
State pattern (More on Design Patterns, Nov 12). Thread-safe queues with many items, thread pools,
and task systems are covered in lectures but not required. Expect about 12 to 15 hours of work in
total.
Your starting point is your own M4. The final project integrates every milestone, so M5 is built on
the M4 you submitted, and no M4 solution is released. If anything in your M4 does not work, fix it
yourself before you build M5 on it: the M3, M4, and CR-1 tests are rerun on your M5 submission.
Record what you fixed in DESIGN.md (Section 9).
2. How M5 is assessed
AI tools are permitted. M5 has no design checkpoint, quiz, or TA interview. Instead, you record a short
walkthrough video of your own code (Section 9). All 20 points are graded from your submission, by
the autograder and by hand (Section 10). Separately, the final exam includes questions about
your own M5 design: your states and how they change, how your worker waits and stops, and
what your code does when an event arrives at an awkward moment. They count toward the final
exam grade, so submit only code you can explain.
3. The problem
M4 kept the corpus build off the GUI thread while the M3 invariant held:
Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.
M4 excluded synchronization, so most M4 designs start new background work for every build, cannot
stop a build once it has started, and track the corpus with flags or an enum checked across
MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?
5. What is fixed and what is your design
Fixed (what the graders depend on):
Everything fixed in M4 stays fixed: the M1/M2 headers and the ProcessingCore API, the M3 GUI
public API and button labels, add_document_file() , set_build_delay_ms() , the rule for
src/main.cpp , and aiws_send with its command line.
Rename your application target from ai_workspace_m4 to ai_workspace_m5 before your
first submission; without it, the autograder cannot run your application. CMake builds
ai_workspace_m5 , aiws_send , and a CTest test named student_tests .
Everything else is your design: your classes, your states, what each state does on each event,
how a request reaches the worker, and how a running build learns that it should stop.
6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.
M5_Specification.pdf 2 / 4
3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,
busy waiting, or sleeping to wait for an event; sleeping is allowed only to simulate build time.
4. Shared data is minimal and named. Every piece of mutable data reachable from two threads
is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.
5. M4 constraints still apply: C++ standard library threading only (no QThread , QtConcurrent ,
QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
the CR-1 socket rules.
7. Testing and fault-detection evidence
A test is worth something only if it fails when the code is wrong. Add each defect below to your code
under its macro, at the place in your design where that behavior is decided, in a few lines.
Macro When defined, your application… Breaks
AIWS_FAULT_NO_CANCEL lets a build that is no longer wanted run to the end, so the
next build waits for it
R3
AIWS_FAULT_SILENT_SHUTDOWN makes Exit hang when no build is running R4
The autograder builds your project normally and once per macro. student_tests must pass on the
normal build and fail within 60 seconds on each faulted build. Neither your test files nor
CMakeLists.txt may mention the macros, and each fault must produce the user-visible defect
described.
Beyond the faults, test R1 to R5 at whatever level your design allows. Tests must be deterministic
and bounded in time.

3. The problem
M4 kept the corpus build off the GUI thread while the M3 invariant held:
Search, Term Inspector, and Context may use only a corpus that is current for the present
Workspace.
M4 excluded synchronization, so most M4 designs start new background work for every build, cannot
stop a build once it has started, and track the corpus with flags or an enum checked across
MainWindow . M5 asks you to remove all three weaknesses; the requirements are in Section 4.
--build-delay-ms N still slows the real build path.
4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?
5. What is fixed and what is your design
Fixed (what the graders depend on):
Everything fixed in M4 stays fixed: the M1/M2 headers and the ProcessingCore API, the M3 GUI
public API and button labels, add_document_file() , set_build_delay_ms() , the rule for
src/main.cpp , and aiws_send with its command line.
Rename your application target from ai_workspace_m4 to ai_workspace_m5 before your
first submission; without it, the autograder cannot run your application. CMake builds
ai_workspace_m5 , aiws_send , and a CTest test named student_tests .
Everything else is your design: your classes, your states, what each state does on each event,
how a request reaches the worker, and how a running build learns that it should stop.
6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.
M5_Specification.pdf 2 / 4
3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,
busy waiting, or sleeping to wait for an event; sleeping is allowed only to simulate build time.
4. Shared data is minimal and named. Every piece of mutable data reachable from two threads
is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.
5. M4 constraints still apply: C++ standard library threading only (no QThread , QtConcurrent ,
QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
the CR-1 socket rules.

4. Required behavior
M5_Specification.pdf 1 / 4
M4 and CR-1 behavior not mentioned here is unchanged. These events drive the corpus lifecycle: a
build is requested; the Workspace changes (Add Document, add_document_file() , or a remote add
through aiws_send ); Reset; a build finishes or fails; and Exit. Which states your application needs,
and how each event moves between them, is your design.
R1 One worker. From the first build until exit, every build runs on the same single build thread;
no thread is created per build.
R2 Handoff. The GUI thread hands a request to the worker without waiting for any build. At most
one build runs at a time, and a request that is already outdated when the worker would take it is
never built.
R3 Cancellation. When an event makes the running build useless, that build stops within about
one document's build time (as set by --build-delay-ms ) and never becomes current. The next
build does not wait for the useless one to run to the end.
R4 Clean shutdown. Exit, at any moment and in any state, stops the worker within about one
document's build time and joins it. The application never hangs on exit.
R5 State pattern. The corpus lifecycle is implemented with the State pattern, under the
constraints in Section 6.
Which event sequences threaten R1 to R4 is for you to work out.
Decisions you must make. The specification deliberately leaves these open. Each has more than
one reasonable answer; yours must be consistent with your code, and DESIGN.md records it (Section
9).
1. Build during a build. May the user request a build while one is running? If so, what happens to
the running build and to the new request?
2. Remote add mid-build. A remote add through aiws_send arrives while a build runs. What
happens to that build, and what does the user see?
3. Shared data. What is the smallest set of data your two threads must share, and why can it not
be smaller?

6. Constraints
1. State pattern. Use the State pattern as presented in lecture (Nov 12): what an event does is
decided by the current state object, not by conditionals elsewhere. No switch or if chain over an
enum, flags, or the type of the current state decides a transition.
2. States stay on the GUI thread. State objects are created, called, and destroyed only on the
GUI thread. The worker never sees them.

3. Waiting. A thread that waits for another uses std::condition_variable , or joins it. No polling,

is protected by a std::mutex or is a std::atomic . DESIGN.md names each one, the threads that
use it, and why that is safe.

QThreadPool , or QFuture ), widgets only on the GUI thread, no detached threads, no owning raw
pointers or manual delete , no processEvents() tricks, connect() with member-function slots, and
